# 砺石 V4 R0 · 页面切换性能诊断

基线 `2217e4ed8a10999914d83dda40bd21c1ed6109db`。用户报告不同板块切换时有轻微卡顿。本轮以八条入口的生产路径、已有测试及历史证据为依据。Android 帧、查询耗时、线程调度、重组次数和真实掉帧均为 `NOT_RUN`。用户感知卡顿的根因为 `UNKNOWN`。

## 八条路径及首要排查项

| 操作 | 当前触发 | 合理怀疑及用于证伪的量 |
| --- | --- | --- |
| 首页 → 回看 | 首访才取得趋势模型，进入触发快照、采样、选日。摘要复用趋势图。 | 先测空壳第一帧与结果帧，用 `loadSnapshot`、`sample`、首个投影的时间区分等待数据和首帧重。 |
| 回看 → 首页 | 趋势 `pause()`，首页项目和订阅双刷新。封面取决于 Scene 挂载与尺寸。 | 比较立即返回和等趋势稳定后返回的窗口排队、取消尾延迟、首页预览封面首帧。 |
| 首页 → 项目列表 | 同一 ProjectViewModel，`loadList()` 重新读取已加载窗口。列表首批卡片可能需封面。 | 同一代无写入时记录读取次数，区分页内 `LazyColumn` 首批测量与封面槽等待。比较有图与无图合成数据。 |
| 项目列表 → 首页 | 双刷新再次触发，首页只消费两类预览各最多两条。读取窗口仍取已加载页数。 | 把项目列表只看首屏与主动加载第二页分组，比较返回时读取行数和响应。卡片数不等于读库条数。 |
| 回看 → 成本趋势 | 同一趋势模型再次 `open()`，前一工作可取消并重读，独立 Scene 首次组合完整趋势图。 | 优先检验相同截止日且未写入的快照启动次数。跟踪一份可见旧图及一次新结果是否让新 Scene 多次准备图形。 |
| 成本趋势 → 回看 | 同一模型再次 `open()`，摘要页面新进场。 | 对比静止返回和刚选日后返回，对齐选日取消、快照、摘要投影及第一帧完整摘要。 |
| 回看 → 年度回顾 | 趋势从活动状态退出，分析模型 `open()`。`IO` 读快照，`Default` 计算类别及年份结果。 | 看上一张趋势计算的取消是否及时，分析快照是否等待同代锁。拆分分析结果发布和首批金额行布局。 |
| 首页 → 设置 | 壳层已有储存用量模型。进入设置启动用量 SQL 汇总，`SettingsShell` 组合纵向页面及状态。 | 比较元数据量、统计锁等待、进入首帧与用量填充帧。若首帧正常且仅数字延迟，归为结果等待。 |

按证据优先排查趋势两层反复触发全量读取，其次排查回首页的双刷新和封面，之后再看年度／设置的数据发布帧。`NavDisplay` 未设场景动画，只能排除当前源码的 enter/exit 动画实现这个具体解释。Nav3 场景变更代价、Compose 重组过多、RenderThread/GPU 和 Android 调度均需实测。前述源码发现尚不足以确认一次实际主线程阻塞、长帧归因、重复同一 SQL 执行的次数或真机回归。

## 最小 Android 采样方案（待实施）

1. **环境与安全**。使用登记身份、独立数据根、无个人账本的测试设备或健康隔离 AVD。确认启动完成、系统 UI 无 ANR、目标包与 runner 签名、UID、隔离根和账号均正确。沿用现有合成账本及 runner 隔离契约。出现历史 ANR 类故障时保留现场并中止此轮。由用户决定是否另行提供真机，避开其日常手机和数据。追踪文件只记录合成标识、阶段名与数量。 [现有隔离准入记录](../../evidence/LITHIC-UI-V4-ICON-NAVIGATION-01.md#2026-11-16--android-再准入) · [现有合成账本测试](../../../app/src/androidTest/java/com/cooper/lithic/performance/LongHistoryPerformanceTest.kt#L65)
2. **固定基准**。以本次 App 树对应的产物为 A，记录 APK 签名、哈希、ABI、Android 版本、显示刷新率、主题、字体、宽度、动画设置、电源和热状态。后续 B 使用同一构建类型和设备。先用固定业务日期的小账本（5 个项目、3 个订阅、90 天内有事实）测八条路由，建立无图和带少量受控封面对照。其次对照有两页项目、真实跨年的合成数据。保留同样的路由和业务完整性。仅在长账本相关且环境健康时重用 M22 的 20 年规模作为压力对照。该历史用例有 `NOT_RUN` 记录，且部分图表宿主独立于生产切换路径。[历史 M22 结论](../../evidence/M22-verification.md) · [真实设备历史边界](../../evidence/M22-Physical-Device-verification.md)
3. **操作序列**。预先等首页总览稳定，每条路径分首访和热回切，首访 3 次独立进程、热回切 10 次，保持账本无写入、同一日期和相同滚动位置。先用悬浮栏及列表「全部」触发正向，用真实返回触发逆向。另做一轮趁趋势读入时往返，单列取消样本。设置、详情、系统返回及未保存防护仍走生产路由。记录 `输入`、`目标首帧`、`内容首次可信呈现`，保留旧结果时分别记录旧值和新结果帧。帧 ID 取系统实际呈现，语义断言只确认内容状态。
4. **可归因的证据**。用 Perfetto 系统 trace 采 `FrameTimeline`、主线程、RenderThread、CPU 调度/频率、GC 和 IO worker。若只有系统 trace 无法对应业务动作，在后续独立诊断分支用测试标记补充路由提交与 Scene 呈现、VM 初次获得、请求／取消／实际结束、锁等待、Room 读、采样／年度计算、封面请求／解码及投影／绘制阶段。按路由汇总超帧比例、最慢帧及帧时间中位数／P95、两个响应时延、查询／读图数和取消时间。保留逐次原始 trace，标明 60Hz/120Hz 下的帧截止时间及系统合成归属。之后需要重复 CI 测量时才考虑独立 Macrobenchmark 模块。[Android 设备系统追踪](https://developer.android.com/topic/performance/tracing/on-device) · [Perfetto FrameTimeline](https://perfetto.dev/docs/data-sources/frametimeline) · [Macrobenchmark](https://developer.android.com/topic/performance/benchmarking/macrobenchmark-overview)
5. **判读与下一步**。若迟帧与主线程投影、Compose layout 或 RenderThread 对齐，优先将展示准备与数据结果更新拆分测量。若多数切换帧按时、可信数据慢，核对同一份数据或日期的多次启动、锁等待及取消。用同一套样本做受控 A/B，比对迟帧和响应时延，列出读取次数及全部未证实项。任何后续数据或生命周期调整都须先验证恢复、待处理操作、按日刷新、图片代次和真实金额语义。R0 结论保持静态诊断，数据不足的条目记为 `NOT_RUN` 或 `UNKNOWN`。
