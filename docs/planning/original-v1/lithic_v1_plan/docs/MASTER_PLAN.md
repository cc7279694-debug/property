# 砺石 LITHIC｜V1 开发总计划

Planning Baseline 1.0 · 2026-10-10  
**范围：规划；不执行产品开发。**

## 1. 总体决策
采用新建纯本地Android项目的路线，不继续对WHOCARE做删除式重构。产品功能仍为已确认的长期项目、固定周期订阅、分类、复盘、趋势、提醒和完整备份。

本次拆成**6个阶段、24个可独立验收的交付模块**。这不是增加24种产品功能，更不是24个Gradle子工程；目的是让一次改动可以解释、测试、验收和停止。

三条主线并行约束全部开发：计算正确、数据可带走、用户真正用得明白。安全恢复不能在用户积累大量记录以后才补。

## 2. 先修正的语义
1. 首页是“已录入有效项目的当前日均成本”，不是今日实际消费或资产价值。
2. 项目按真实持有自然日计时；结束后时间冻结，但真实退款和分期尾款仍可改变历史结算。
3. 订阅30/90/365是标准已购时长，明确叫“折算付费时长”，不叫“已经用了这么久”。
4. 真正的订阅里程碑按已经过去的付费有效时间；预付一年当天不能解锁一年陪伴。
5. 订阅到期而未记录续费自动不再计入；提前付下一期不提前切换当前价格。
6. 取消服务商自动续费和本App记录停止不是同一动作；默认尊重已付剩余期。
7. 以旧换新按用户确认的完整取得成本记录，但标明非现金折抵，避免把折抵说成现金。
8. 备份先校验后覆盖，且完整恢复包含库、图片和设置；不能“先清空再试试看”。

详细算法、边界和例子见DOMAIN_CONTRACT，这些均是本轮补齐的工程解释，不声称用户曾逐项回答过。

### 阶段B｜可安全使用的核心版（M06–M13）

两条业务闭环+完整备份恢复+首页，之后才承载长期真实数据。

## 4. 依赖与交付门槛
推荐按编号串行执行。当前阶段内只有不共享状态的测试/文案审阅可独立检查，不让多个Codex任务同时改核心数据库或同一业务引擎。

G0（M05）：领域规则、存储与页面骨架可验证，仍主要用合成数据。

G1（M13）：长期项目+订阅+完整备份恢复+首页闭环通过，形成第一个可用稳定签名内部版。用户可以开始录入真实数据；这不代表全部V1完成。

G2（M19）：分类、搜索、历史、替换、项目/总趋势、类别/年度回顾完整。

G3（M21）：两种通知通过授权、去重、过期和重建验证，不承诺系统省电下准点。

G4（M23）：升级/格式迁移/恢复故障/小屏/长历史/签名交付全部关键门槛满足，独立验收后冻结V1。

M06或M09后可以给你装Debug演示体验；但在恢复验证完成、签名身份稳定前，不把它作为唯一真实记录本。

## 5. 数据库与备份配对演进
M04 schema v1；M08 schema v2；M11 backup v1；M16 schema v3+backup v2；M20 schema v4+backup v3。每次新增字段同时补备份与迁移，不把未来安全修复变成欠账。
只有事实进入数据库，金额结果、排行和曲线是派生结果。数据表数量服务于一致性，不以“必须只有两张表”制造错误。

## 6. 页面不是实现清单的镜像
主导航仅现在/回看/设置。现在承载总成本与类别；项目和订阅独立列表；回看承载历史、榜单、趋势、类别、年度；设置承载备份、提醒与说明。
24模块全部完成后，用户仍不应面对24个顶层按钮。

## 7. 执行和验收
每次仅授权一个模块。实现者先测试再实现，写实际完成报告；独立验收检查差异、测试证据、关键流程、schema与备份完整性。实现者最多READY_FOR_REVIEW，不自封ACCEPTED。
不能通过“测试很多”“构建成功”“APK能打开”替代金额正确、离线可用和恢复不丢数据。
未跑项目写NOT_RUN；坏备份破坏现有记录、错算成本、重复付款、升级丢数据和越界联网都属于阻断。

## 8. 计划里不放什么
不估交付日期、不承诺一口气做完、不根据模型名字推断测试可靠性。不额外加AI、云同步、目标、预测、预算、估价、打卡、账单自动导入和平均使用寿命。
不在当前对话创建外部仓库或资源，不修改WHOCARE，不把开发授权混入规划。

## 9. 下一工作单元
下一次实际工作先从M00文档契约落地开始；其范围只有新工程事实源与状态登记。随后用户授权M01，再建立可安装的Android空壳。具体可复制入口见templates/EXECUTE_ONE_MODULE.md。

## 10. 平台技术依据
采用Android官方的分层、单向流与Repository建议；系统备份、WorkManager调度、通知权限和签名升级都有平台边界，不能把产品偏好当系统能力。来源与逐项使用范围见SOURCES.md。
